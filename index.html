Troubleshooting

[SuperPoint SLAM] 디스크립터 헤드 붕괴로 루프 클로저가 불가능했던 문제
  • 문제 · 직접 학습한 경량 모델로는 인접 프레임 매칭 inlier가 7%에 그쳐, 진짜 루프와 가짜 루프를 구분할 수 없었습니다.
  • 원인 · 학습 중 디스크립터 헤드가 붕괴해 모든 키포인트의 기술자가 사실상 같은 벡터로 수렴했습니다(프레임 내 유사도 p95 0.999).
  • 해결 · 백본과 검출 헤드는 동결하고, 디스크립터 헤드(74.6K 파라미터)만 원본 SuperPoint를 teacher로 재증류했습니다(KITTI 이미지 6천 장, 2 epochs, 약 2분).
  • 결과 · 인접 프레임 inlier 7% → 89%, 진짜 루프쌍 inlier 7% → 74%로 회복해 루프 클로저를 다시 쓸 수 있게 되었습니다.
[SuperPoint SLAM] 루프 클로저의 오탐과 스케일 드리프트
  • 문제 · 단안 카메라 SLAM은 이동 거리가 늘수록 스케일이 어긋나고, 비슷하게 생긴 다른 장소를 같은 장소로 잘못 인식하면 지도 전체가 틀어집니다.
  • 원인 · 후보 검색에 max-pooling 기술자를 쓰면 값이 포화되어 모든 이미지 쌍의 유사도가 1.0이 되었고, 회전·위치만 보정하는 방식으로는 스케일 오차가 남았습니다.
  • 해결 · mean-pooling 기술자를 평균만큼 빼는 centering 후 코사인 유사도로 후보를 찾고, PnP(실패 시 Essential Matrix)로 검증했습니다. 검증 임계값은 KITTI 실측(진짜 루프 92 vs 가짜 9~14 inliers)으로 정하고, 보정은 g2o Sim3(7-DOF) Pose Graph Optimization으로 전환해 스케일까지 교정했습니다.
  • 결과 · KITTI 07에서 시작-끝 폐합 오차 38.5m → 25.4m, 루프가 없는 KITTI 08에서는 후보 460개를 전부 기각해 오탐 0건을 기록했습니다.
[SuperPoint SLAM] GPU가 오히려 느렸던 특징점 매칭
  • 문제 · 실시간성을 위해 매칭을 GPU(Apple MPS)로 돌렸지만 기대만큼 빨라지지 않았습니다.
  • 원인 · 매칭에 쓰는 행렬이 작아 GPU 커널을 호출하는 오버헤드가 계산 이득보다 컸고, 실측해 보니 CPU가 MPS보다 6배 빨랐습니다.
  • 해결 · CUDA 환경에서만 GPU 매칭을 쓰도록 매처 디바이스를 분기하고, 필터와 시각화 렌더링을 최적화했습니다. 입력 자동 축소(640px)는 속도 이득 없이 정확도만 떨어뜨려(ATE +41%) 원본 해상도를 쓰도록 했습니다.
  • 결과 · 프레임당 약 15ms를 단축했습니다.
[SuperPoint SLAM] 일반 영상과 다른 가중치 파일에서 SLAM이 동작하지 않던 문제
  • 문제 · 입력 해상도가 640×480, 초점거리가 블랙박스 화각으로 고정되어 있어 다른 영상에서는 맞지 않았고, 다른 방식으로 저장된 가중치 파일은 로드되지 않았습니다.
  • 원인 · SuperPoint는 입력 가로·세로가 8의 배수여야 하는데 원본 해상도와 비율을 고려하지 않았고, 가중치 로더가 state_dict로 감싼 체크포인트와 멀티 GPU 학습의 module. 접두사를 처리하지 못했습니다.
  • 해결 · 영상의 실제 해상도를 읽어 비율을 유지한 채 8의 배수로 맞추고, 초점거리를 화면 크기에서 추정하도록 바꿨습니다. 두 가지 체크포인트 형식을 모두 읽도록 로더를 고쳤습니다.
  • 결과 · 블랙박스 영상에 한정되지 않고 일반 MP4 영상과 다양한 형식의 가중치로 SLAM을 실행할 수 있게 되었습니다.
[LG Aimers] 랜덤 검증으로는 잡히지 않던 시즌 과적합
  • 문제 · CatBoost를 랜덤 홀드아웃 조기 종료로 약 2,000그루까지 학습시키자, 시간 분할 검증 점수가 오히려 501 → 454로 떨어졌습니다.
  • 원인 · 과거 시즌으로 학습해 다음 시즌을 맞혀야 하는 문제라 과적합이 '시즌' 단위로 일어났고, 같은 시즌 안에서 무작위로 뗀 검증셋은 이를 잡지 못했습니다.
  • 해결 · 2019~2023년으로 학습하고 2024년으로 검증하는 시간 기준 용량 스윕으로 적정 트리 수를 찾고, 이후에는 시간 분할 조기 종료의 평균 반복 수로 학습 횟수를 고정했습니다. 평가지표가 MSE 기반이라 분류 모델을 회귀(RMSE) 모델로 바꿔 지표를 직접 최적화했습니다.
  • 결과 · 약 280그루에서 정점을 찾아 시간 분할 점수 706.22를 확보했고, 회귀 전환으로 +8.28을 더해 이후 Public 1014.37 → 1035.07까지 개선했습니다.

[LG Aimers] 팀 아이디어를 이식했다가 점수가 떨어져 롤백한 경험

  • 원인 · 배포용으로 재학습한 모델을 별도 검증셋으로 다시 확인하지 않았고, 스태킹 계수와 보정값(intercept)을 검증 없이 재사용한 것을 원인으로 판단했습니다.
  • 해결 · 이전 최고 모델(exp180)로 즉시 롤백하고, 원인을 팀 실험 원장에 기록했으며 최종 모델 설명 문서를 작성했습니다.
  • 결과 · 최고 기록을 유지했고, 재학습한 배포 모델과 재사용한 계수는 반드시 다시 검증해야 한다는 교훈을 팀 원장과 저장소 문서에 남겼습니다.
[LG Aimers] 작은 성능 향상이 진짜인지 순열검정으로 확인
  • 문제 · 세 번째 모델(NODE)을 스태킹에 추가하자 +2.49가 나왔지만, 모델 간 상관이 높아(0.935~0.957) 다중공선성으로 인한 착시일 가능성이 있었습니다.
  • 해결 · NODE 예측을 무작위로 섞은 뒤 같은 20-fold 비교를 5번 반복하는 순열검정을 설계했습니다.
  • 결과 · 순열 결과는 노이즈 범위(-1.67 ~ +1.96, 평균 -0.65)에 흩어진 반면 실제 NODE는 20번 중 20번 모두 우세해, 향상이 우연이 아님을 확인했습니다.
[TimeFit] 프론트엔드와 백엔드 연동 시 회원가입이 동작하지 않던 문제
  • 문제 · 프론트엔드와 백엔드를 연결하자 회원가입 요청이 정상적으로 처리되지 않았습니다.
  • 원인 · 프론트엔드가 보내는 회원가입 정보(이름 또는 회사명, 연락처, 주소)를 백엔드 요청 형식이 받지 못했고, 서버에 CORS 설정이 없어 다른 출처에서 오는 브라우저 요청이 막혔습니다.
  • 해결 · 백엔드 회원가입 요청·사용자 모델에 필드를 추가하고, 구직자 이름과 채용자 회사명 중 있는 값을 쓰도록 했습니다. Spring Security에 CORS 설정을 추가하고, 가입 직후 JWT를 발급해 바로 로그인되도록 했습니다.
  • 결과 · 구직자·채용자 모두 회원가입부터 로그인까지 프론트엔드와 백엔드가 연결되었습니다.
